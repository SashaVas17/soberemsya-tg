## 1. Пожелания и правила владельца

### Процесс
- Не начинать проект заново и не переписывать существующую архитектуру.
- Перед изменениями проверять репозиторий, ветку, HEAD/origin-main, чистоту дерева.
- Стандарт проверки: `npm test`, `npm run lint`, `npm run build`, `git diff --check`,
  `deno check` для `telegram-api` и `telegram-bot`. Базовая линия — 659/659 тестов.
- Windows/PowerShell: `npm.cmd` / `npx.cmd` / `pnpm.cmd`; не просить менять execution policy.
- Работа ведётся в Claude, конвенция «модель/effort/skills» адаптирована под Claude (см. п. 5).

### Безопасность
Никогда не просить вставить или показать: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`,
`TELEGRAM_DB_SECRET_KEY`, `TELEGRAM_CALENDAR_SIGNING_SECRET`, service-role ключи, `sb_secret_*`,
access-токены Supabase, пароли БД, connection strings, `.env`, реальные `initData`.

### База данных
- Запрещено: `supabase migration list`, `supabase db push`, `supabase db reset`, `migration repair`,
  `migration pull`, `--include-all`, произвольные прямые подключения к PostgreSQL.
- Production DDL — только через подключённую возможность Supabase migration-apply (выполняет Claude через Supabase-коннектор, когда он подключён).

### Продуктовые решения, уже принятые
- Идемпотентность `update_id` в telegram-bot отложена: единственный побочный эффект — внешний
  `sendMessage`, честного exactly-once через таблицу `processed_updates` не получить. Не делать фиктивное решение.
- Атомарное создание встречи уже сделано. Следующий архитектурный приоритет — идемпотентность запроса
  создания (потерянный HTTP-ответ + повтор = дубликат встречи).
- Не выполнено: QA предложений вариантов участником со второго аккаунта/устройства.

## 2. Анализ проекта

### Сильные стороны
- Защищённая архитектура: подпись `initData` проверяется на сервере (TTL 1 ч); браузер не ходит в таблицы;
  RLS + revoke; service-role только в Edge Functions; `security definer` RPC с фиксированным `search_path`;
  лимиты размера JSON; CORS по allowlist; безопасные коды ошибок.
- Критичные мутации — атомарные RPC (создание, сохранение ответа, предложения вариантов, заявки).
- Keyset-пагинация, автоархивация через pg_cron.
- 659 тестов, lint, strict TypeScript; CI прогоняет lint/test/build перед деплоем Pages.
- Mock-режим для локальной разработки без Telegram и БД.
- Минимум зависимостей (React, supabase-js, lucide), лёгкий бандл (~81 КБ gzip JS).
- Продуманный UX: дизайн-система Light/Dark, мастер создания, итог + календарь, протестировано на телефоне.

### Слабые стороны и риски
1. **Нет уведомлений.** Бот только отвечает на `/start`, `/new`, `/my`, `/help`. Организатор не узнаёт
   о новых ответах/заявках, участники — об итоге, нет напоминаний перед встречей. Главный продуктовый пробел.
2. **Монолит фронтенда:** `src/App.tsx` ~2940 строк, 76 `useState`; `styles.css` ~3170 строк;
   самописная навигация, нет слоя кеширования данных. Каждая новая фича дороже и рискованнее.
3. **Тесты без рендера:** окружение `node`, часть UI-тестов проверяет текст исходников. Нет компонентных
   и E2E-тестов (Playwright доступен), сценарии «два аккаунта» проверяются только вручную.
4. **Нет наблюдаемости:** ни трекинга ошибок, ни продуктовой аналитики → нельзя измерить удержание и
   принять решение о мобильном приложении на данных.
5. **Нет защиты от спама и модерации** открытых встреч: нет rate limit, жалоб, блокировки.
6. **Открытые встречи без города/категорий/поиска/карты** — лента одна на всех.
7. **Идемпотентность создания встречи** (запланирована).
8. **TTL `initData` 1 час:** если Mini App открыт дольше часа, запросы получат 401 до переоткрытия (проверить).
9. **Процесс релиза:** CI только на push в `main` (PR не проверяются), нет `deno check` в CI, деплой функций
   и миграции вручную; в репозитории два lock-файла (`package-lock.json` и `pnpm-lock.yaml`).
10. `telegram-api/index.ts` ~1030 строк с роутингом на регулярках — терпимо, но растёт.

## 3. Мобильное приложение Android/iOS — вывод

Сейчас не стоит. Telegram даёт бесплатно то, на чём держится продукт: вход без регистрации, доставку
ссылки в групповой чат, мгновенное открытие у приглашённых. Нативное приложение потребует собственного
входа (Apple требует Sign in with Apple при соцлогинах), push-инфраструктуры, удаления аккаунта,
модерации UGC (правило App Store 1.2 — жалобы/блокировка для открытых встреч), веб-фолбэка для тех,
у кого приложения нет, и аккаунтов разработчика (Apple $99/год, Google $25 разово).

Рекомендуемый путь:
1. Уведомления через бота + аналитика → измерить удержание.
2. Веб-версия вне Telegram (тот же React, вход через Telegram Login) — проверка спроса вне Telegram.
3. Если метрики оправдывают — обёртка Capacitor над тем же кодом, а не переписывание на Swift/Kotlin.
