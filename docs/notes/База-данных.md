# База данных

Supabase PostgreSQL, проект `qesuhhhiswwrfvfisfkp`. Миграции — `supabase/migrations/`.

## Таблицы
- Встречи: `events`, `time_options`, `place_options`, `participants`, `availability_votes`, `place_votes`,
  `join_requests`, `event_creation_requests` (идемпотентность создания).
- Города: `cities` (`id`-слаг, `name`, `timezone`, `is_active`, `sort_order`). Активен только Минск;
  Брест, Витебск, Гомель, Гродно, Могилёв — выключены до этапа 4. Города не удаляются, только выключаются.
- Пользователи: `users` (в т. ч. `can_message`, `city_id` — выбранный город, `null` = Минск), `notification_preferences`.
- Категории: `meeting_categories` (`id`-слаг, `name`, `sort_order`, `is_active`): кофе, бар, спорт, настолки,
  прогулка, кино, концерт, активный отдых, другое, ресторан (`food`, добавлен на этапе 2.3). Новая категория — `insert`, выключить — `is_active = false`
  (таблица вместо check-ограничения: менять список без `drop`). У встречи `events.category_id` (необязательна).
- Создание с категорией — RPC-обёртки `create_event_categorized` / `create_event_idempotent_categorized`: вызывают
  прежние `create_event_atomic` / `create_event_idempotent` и в той же транзакции ставят категорию. Повтор с тем же
  ключом возвращает созданную встречу до проверки категории (иначе выключенная категория превращала бы повтор
  в 400 и дубль); хэш запроса включает категорию, только если она задана.
- У встречи `events.city_id` (not null). Если город не передан, триггер `events_set_city_from_owner`
  берёт активный город организатора, иначе Минск; явно переданный город сохраняется.
- Уведомления: `notification_outbox`, `event_notification_state` — см. [Уведомления](Уведомления.md).
- Группы: `event_group_chats`, `group_links`, `group_message_outbox`.
- Аналитика: `analytics_events`.
- Модерация (этап 2.4): `users.banned_at` (ограничен администратором), `users.community_rules_accepted_at`,
  `events.hidden_at` (скрыта из ленты); `user_blocks` (кто кого заблокировал, до 200 на человека; имя и @username в списке — только если блокирующий видел их раньше, т. е. организатор блокирует участника/автора заявки; организатор, заблокированный из превью, подписан названием встречи — превью его не раскрывает), `reports`
  (жалобы: на встречу — `target_type = 'event'`, `target_user_id` — её организатор; на человека — `'user'`), `action_rate_limits` (лимиты в час/сутки — меняются `update`
  без релиза) и `action_rate_log` (журнал действий за двое суток).
- Лимиты: `consume_action_rate_limit(user, action)` — advisory-lock на пару «пользователь + действие», счёт за
  час и сутки, запись. Вызывается после самого действия, поэтому `RATE_LIMITED:<action>` откатывает его
  целиком. Обёртки: `create_event_categorized`/`create_event_idempotent_categorized` (повтор по ключу не
  считается; открытые встречи — ещё бан), `create_join_request_moderated` (бан, скрытая встреча, блокировка,
  счёт только новых заявок), `propose_event_*_option_limited`. Жалобы — `create_report` (повтор не считается,
  администраторам — уведомление `report_new`), блокировки — `block_user`/`unblock_user`/`list_user_blocks`,
  администратор — `admin_reports`, `admin_resolve_report`, `admin_set_event_hidden`, `admin_set_user_banned`
  (бан скрывает все открытые встречи человека — даже с итогом, чтобы «Снова собрать ответы» не вернуло её
  в ленту; снятие бана их не возвращает). Заявка на встречу ограниченного организатора отклоняется.
- Каталог мест (этап 2.3): `venues` — город, категория, название, адрес, координаты, `price_level` (1 — до 20,
  2 — 20–50, 3 — от 50 BYN на человека; ставит куратор), сайт, часы работы, `source` (`osm`/`manual`),
  `osm_type`+`osm_id` (уникальная пара), `status` (`pending` → `published`/`hidden`), `featured` («Рекомендуем»,
  первыми в выдаче). Места не удаляются, только скрываются. `service_role` читает таблицу напрямую
  (`grant select`), изменения — RPC `admin_import_venues` (upsert по OSM-ключу: новые — `pending`, у известных
  обновляются только OSM-поля, решения куратора не трогаются, неизменённые строки не пишутся),
  `admin_create_venue` (ручное место, сразу опубликовано), `admin_update_venue`, `admin_publish_venues`.
  Платное продвижение, если появится, — отдельной таблицей, `featured` — только выбор куратора.
- Лента открытых встреч — `public_feed_page(viewer, city, category, pattern, cursor…)`: без скрытых встреч и
  встреч людей, с которыми есть блокировка в любую сторону (`not exists` по `user_blocks`), keyset-пагинация
  по `(created_at, id)`. Одна открытая жалоба на встречу/человека от автора; после закрытия можно снова.

## Правила
- Новые таблицы не дают `service_role` прав на данные по умолчанию: для чтения из функции нужен явный
  `grant select on table public.<t> to service_role;` (урок 2026-10-14: без него упала лента после релиза городов;
  тогда же нашлось, что `place_votes` тоже не читалась). Проверка — `tests/service-role-grants.test.ts`.
- Все таблицы с RLS, без прав у `anon`/`authenticated`. Изменения — атомарные RPC `security definer`
  с `set search_path = pg_catalog, public`, доступ только у `service_role`.
- Миграции продакшена — **только** через Supabase-коннектор (`apply_migration`). Запрещены
  `supabase db push/reset`, `migration repair/pull/list`, `--include-all`, прямые подключения.
- После применения — переименовать файл под версию Supabase и сверить текст со
  `supabase_migrations.schema_migrations.statements`.
- Баг коннектора: зависает на `drop ...`, на `raise` + `delete` в одном теле функции, на двух `delete` в одном
  теле. Обходы — `create or replace trigger`, каждый `delete` в отдельной функции без `raise`.
  `alter table ... drop constraint ..., add constraint ...` проходит (2026-10-14, расширение типов уведомлений).
- Локальная проверка: Postgres 16 с заглушками `auth`, `vault`, `cron`, `extensions`, все миграции по порядку,
  сценарии с параллельными запросами.
