# Безопасность

Как защищены проект и данные пользователей, что проверено, что делать при утечке. Названия секретов —
в [Настройки и секреты](Настройки-и-секреты.md) (значения никогда не записываются).

## Как устроена защита

| Слой | Что защищает | Как |
|---|---|---|
| Вход | Кто вызывает API | Каждый запрос к `telegram-api` несёт initData Telegram; подпись проверяется ключом `WebAppData` и сравнивается за постоянное время, срок — 1 час. Без подписи открыты только `/health` и ссылка календаря, подписанная HMAC на 10 минут. |
| Доступ к данным | Чужие встречи и ответы | Роль считается на сервере (организатор / участник / приглашённый по ссылке); у открытых встреч посторонний видит только превью. Админские маршруты отвечают 404 всем, кроме `TELEGRAM_ADMIN_IDS`. |
| База | Прямой доступ к таблицам | RLS на всех 23 таблицах без политик; у `anon`/`authenticated` нет прав ни на таблицы, ни на функции `public`; все RPC — `security definer` с фиксированным `search_path`, вызывает только `service_role`. Публичный ключ из сборки ничего не открывает. |
| Злоупотребления | Спам и засорение базы | Лимиты `action_rate_limits` (создание встреч, заявки, предложения, жалобы); потолок аналитики — 200 событий на человека в час; размер тел запросов ограничен. |
| Бот | Подделка вебхука | Заголовок `x-telegram-bot-api-secret-token`, сравнение за постоянное время. Сообщения — простой текст (без `parse_mode`), названия встреч не превращаются в разметку. |
| Фронтенд | Внедрение скриптов | Нет `dangerouslySetInnerHTML`; CSP в продакшен-сборке (`csp.ts`): скрипты только свои и `telegram.org`, сеть — только API и тайлы карты. Моки в продакшене выключены принудительно. |
| CI/CD | Подмена зависимостей | Actions закреплены по SHA, Supabase CLI — по версии; токен Supabase виден только шагу деплоя; права Pages — только задаче деплоя; CI на PR без секретов; Dependabot. |
| Репозиторий | Утечка секретов | Секретов в коде и истории нет (проверено 2026-10-15); включены Secret scanning и Push protection. |

## Проверка 2026-10-15

- Живая база: Supabase Security Advisor — только «RLS без политик» (так задумано) и «защита от утёкших паролей»
  (не относится: вход через Telegram, Supabase Auth не используется). Права `anon`/`authenticated` на `public` — нет.
  Секретов в `cron.job` — нет. Хранилище Storage пустое.
- Код: все маршруты `telegram-api` — проверка подписи, ролей и админа; изменения передают в RPC только
  `auth.user.id`, управление встречей начинается с `assertOwner`. Доступа к чужим данным (IDOR) не найдено.
- Найдено и исправлено: засорение `analytics_events` через `/me/analytics` с разными `eventId`; сравнение секрета
  вебхука через `!==`; права деплоя шире нужного; незакреплённые версии в CI; нет CSP.
- Зависимости: `npm audit` по продакшен-пакетам — 0 уязвимостей; функции используют `supabase-js` точной версии.
- Сторонние навыки `mukul975/Anthropic-Cybersecurity-Skills` (54a7988) просмотрены и **не установлены**: общие
  тексты с ошибками в примерах, 818 навыков раздули бы контекст, есть скрипты.

## Сделать владельцу (кнопки в интерфейсах)

GitHub → репозиторий → **Settings**:
1. **Advanced Security** (или «Code security»): включить **Dependabot alerts**, **Dependabot security updates**,
   **Private vulnerability reporting**, **CodeQL analysis → Default**. Secret scanning и Push protection уже включены.
2. **Actions → General → Workflow permissions**: «Read repository contents and packages permissions»;
   снять «Allow GitHub Actions to create and approve pull requests».
3. **Rules → Rulesets → New branch ruleset**: цель — `main`, включить **Restrict deletions** и
   **Block force pushes**, без исключений. «Require a pull request» **не включать**, пока Obsidian пушит заметки
   прямо в `main` (иначе резервные копии хранилища перестанут уходить).

Аккаунты: двухфакторная защита (лучше passkey) в GitHub, Supabase и Cloudflare; облачный пароль в Telegram
(Настройки → Конфиденциальность → Облачный пароль) — от аккаунта Telegram зависят бот и права администратора.

Supabase → **Authentication → Sign In / Providers**: выключить **Allow new users to sign up** и провайдер Email —
приложение входит через Telegram, а открытая регистрация даёт лишние учётные записи. В **Authentication → Users**
есть одна тестовая учётная запись от 2026-08-02 (ни разу не входила, прав не имеет) — можно удалить.

Supabase → **Account → Access Tokens**: `SUPABASE_ACCESS_TOKEN` в GitHub — личный токен с доступом ко всем
проектам аккаунта. Создать новый с понятным именем («github deploy flockly»), заменить секрет в GitHub
(Settings → Secrets and variables → Actions), старый отозвать. Ставить срок действия и менять раз в год.

## Если секрет утёк

Порядок: сменить → обновить там, где используется → проверить → отозвать старый. Значения не пересылать в чат.

| Секрет | Где сменить | Что ещё сделать |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | BotFather → `/revoke` | Новый токен — в секреты Supabase; запустить `scripts/configure-telegram.sh` (вебхук). |
| `TELEGRAM_WEBHOOK_SECRET` | Придумать новый | Секреты Supabase + `scripts/configure-telegram.sh`. |
| `TELEGRAM_DB_SECRET_KEY` (серверный ключ Supabase) | Supabase → Project Settings → API Keys → новый secret key | Обновить секрет функций, проверить логи на 5xx, удалить старый ключ. **Самый ценный**: даёт полный доступ к базе. |
| `TELEGRAM_CALENDAR_SIGNING_SECRET` | Новый случайный | Секреты Supabase; старые ссылки календаря (10 мин) перестанут работать — это нормально. |
| `notifications_worker_secret` | Supabase Vault | Миграцией обновить значение в Vault (воркер читает его оттуда). |
| `SUPABASE_ACCESS_TOKEN` | Supabase → Access Tokens | Секрет GitHub; старый отозвать. |

После любой утечки: Supabase → Logs (функции, 5xx и необычные IP), GitHub → Security, Telegram → активные сеансы.

## Правила на будущее

- Новый внешний хост во фронтенде — добавить в `csp.ts`; проверка `e2e/csp.spec.ts` упадёт, если забыть.
- Новое GitHub Action — только по SHA с комментарием версии (`tests/security-hardening.test.ts`).
- Новая таблица — RLS + `revoke ... from public, anon, authenticated`; новая функция — `security definer`,
  `set search_path = pg_catalog, public`, `revoke execute` и `grant execute ... to service_role`.
- Новое действие, которое пишет в базу, — подумать о лимите в `action_rate_limits`.
- Раз в месяц: Supabase Security Advisor, Dependabot, `npm audit --omit=dev`.

## Открытые решения владельца

- Репозиторий публичный: код и хранилище Obsidian (`docs/` — монетизация, конкуренты, идеи) видны всем. Варианты:
  сделать репозиторий приватным (проверить, что хостинг сайта это допускает) или перенести хранилище в отдельный
  приватный репозиторий. Секретов в репозитории нет — публичность не даёт доступа к данным.
- Лицензии нет — по умолчанию все права у владельца.
- В авторе старых коммитов видны имя и имя компьютера; на будущее — `noreply`-почта GitHub в настройках git.
