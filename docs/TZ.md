**Известные проблемы**
- Публичные серверы Overpass не отвечают облаку Supabase; если приложение администратора тоже не получает ответ,
  сообщение покажет, что ответил каждый сервер (`overpass-api.de`, `private.coffee`, `kumi`).
- Меню кнопки «Открыть Flockly» одно на всех: у Telegram нет её перевода.
- В облаке Claude нет браузера под Playwright 1.64: `npm run test:e2e` запускать с временным конфигом
  (`launchOptions.executablePath` = `/opt/pw-browsers/chromium-*/chrome-linux/chrome`, `--no-sandbox`), в CI всё штатно.
- 2026-10-22 истёк `SUPABASE_ACCESS_TOKEN` (деплой функций — 401); владелец обновил. Если деплой функций снова
  401 — обновить токен в GitHub → Secrets → Actions.

## 1. Цель и позиционирование

Стартап для широкой аудитории, не только для друзей. Формат — Telegram Mini App; нативных приложений пока нет.

Два сценария одного продукта:
1. **Со своими** — быстро договориться с компанией о времени, месте и бюджете (уже работает).
2. **С новыми людьми** — найти открытую встречу или место в своём городе и присоединиться.

Сквозная фишка — **подборка заведений**: где провести время, с учётом бюджета и типа встречи.

География: Минск → областные центры (Брест, Витебск, Гомель, Гродно, Могилёв) → другие страны.
Сейчас пользователей двое (владелец и друг), поэтому главная метрика ближайших этапов — **рост и удержание**.
Монетизация — позже, не в этом ТЗ, но модель данных не должна ей мешать.

## 2. Неизменные правила

- Не переписывать архитектуру: React + Vite + TS, Supabase Edge Functions + PostgreSQL, GitHub Pages.
- Секреты никогда не запрашиваются и не попадают в чат, код или логи (полный список — `PROJECT_NOTES.md`).
- Production DDL — только через подключённый Supabase-коннектор (`apply_migration`). Запрещены
  `supabase db push/reset`, `migration repair/pull/list`, `--include-all`, прямые подключения к PostgreSQL.
- Порядок релиза любой фичи: миграция → Edge Function → фронтенд. Каждый шаг обратно совместим с предыдущим.
- Никакого фиктивного exactly-once для внешних побочных эффектов (сообщения Telegram). Гарантии называть честно.
- Для каждого PR перед мержем: `npm test`, `npm run lint`, `npm run build`, `git diff --check`,
  `deno check` обеих функций, `/code-review`; для бэкенда/БД ещё `/security-review`.

## 4. Этапы

### Этап 0. Фундамент надёжности (короткий)

**0.1 CI на pull request.** Новый workflow: lint, test, build и `deno check` обеих функций на каждый PR.
Деплой Pages — по-прежнему только из `main`.

**0.2 Идемпотентность создания встречи.**
- Таблица `event_creation_requests (owner_user_id, client_request_id uuid, request_hash, event_id, created_at)`,
  PK `(owner_user_id, client_request_id)`, доступ закрыт для `anon`/`authenticated`.
- RPC `create_event_idempotent`: запись ключа и создание встречи в одной транзакции.
  Повтор с тем же ключом и тем же содержимым → та же встреча (HTTP 200). Тот же ключ с другим содержимым → 409.
  Параллельные повторы сериализуются уникальным индексом.
- `POST /events` принимает необязательный `clientRequestId`; без него поведение прежнее.
- Фронтенд: ключ создаётся на черновик, переживает перезагрузку, переиспользуется при повторе после сетевой
  ошибки, сбрасывается после успеха или изменения черновика.
- Ключи старше 30 дней удаляются задачей pg_cron.

**0.3 Истечение `initData`.** Сейчас TTL 1 час: Mini App, открытый дольше, получает 401 на всё.
Фронтенд при 401 показывает понятный экран «Сессия Telegram устарела → Открыть заново».
TTL не увеличивать без отдельного решения.

**0.4 Дымовой E2E.** Playwright в mock-режиме: создать встречу → открыть → проголосовать → итог.

**0.5 Lock-файл.** Оставить один (`package-lock.json`, его использует CI); убрать противоречие с `.gitignore`.

Приёмка: PR-проверки работают; двойная отправка создания (в том числе при обрыве ответа) даёт одну встречу;
тесты на повтор, конфликт и параллельные запросы; 401 показывает экран переоткрытия.

### Этап 1. Уведомления и рост через Telegram

**1.1 Разрешение на сообщения.** При первом действии, которому нужны уведомления, вызывать
`Telegram.WebApp.requestWriteAccess()`; хранить `users.can_message`. Без разрешения бот не пишет.

**1.2 Очередь уведомлений (outbox).**
- Таблица `notification_outbox` пополняется внутри тех же транзакций, что и бизнес-изменения.
- Отправку выполняет отдельная Edge Function `notifications-worker`, её раз в минуту вызывает pg_cron через pg_net.
- Гарантия: **at-least-once** с ключом дедупликации на событие. Дубль возможен только при сбое между
  `sendMessage` и отметкой об отправке — это документируется, а не маскируется.
- Уважать лимиты Telegram (429 + `retry_after`), до 5 повторов, затем статус `failed`.

**1.3 Какие уведомления.**
- Организатору: новый ответ участника (группировка — не чаще 1 сообщения в 15 минут на встречу),
  новая заявка в открытую встречу, участник предложил вариант, участник вышел.
- Участникам: встреча изменена организатором, выбран итог (время и место), встреча отменена, заявка одобрена/отклонена.
- Напоминания по желанию: за 24 часа и/или за 2 часа до встречи (выбор пользователя, по умолчанию выключены).
- Настройки уведомлений в профиле: включить/выключить по типам.
- Каждое сообщение — кнопка, открывающая нужный экран Mini App.

**1.4 Богатая отправка в чат.** Вместо голой ссылки — карточка встречи с кнопкой «Проголосовать»
(`savePreparedInlineMessage` + `WebApp.shareMessage`, inline-режим бота). Старый способ — запасной.

**1.5 Бот в группах.** Добавить бота в группу → `/new` создаёт встречу для группы, карточка публикуется в чат,
итог публикуется туда же. Учесть: в группах бот видит только команды (privacy mode).

**1.6 Базовая аналитика (без сторонних сервисов).**
- Таблица `analytics_events` (событие, пользователь, источник `startapp`, время), минимум событий:
  открытие приложения, создание встречи, ответ, заявка, переход из уведомления, отправка в чат.
- Экран «Статистика» для администратора: DAU/WAU, созданные встречи, ответы, доля вернувшихся за 7 дней,
  конверсия «приглашение → ответ».

Приёмка: уведомления приходят на второй аккаунт; настройки работают; повтор воркера не шлёт дубль в
нормальном режиме; карточка отправляется в личный и групповой чат; статистика видна только администратору.
Здесь же проводится отложенный QA предложений вариантов со второго аккаунта.

**Решения владельца по этапу 1 (2026-10-13)**
- Организатор сам выбирает режим уведомлений об ответах: «каждый ответ» (не чаще 1 сообщения в 15 минут на встречу)
  или «сводка» (по умолчанию): одно сообщение, когда ответили все приглашённые или раз в день —
  «ответили N, подходит M, отказались K».
- Участники получают только важное: изменение встречи организатором, итог, отмену, решение по заявке.
  Об ответах других участников не пишем.
- Новое действие «Отменить встречу» (статус `cancelled`, встреча остаётся в истории, участники получают уведомление);
  «Удалить» остаётся отдельно.
- Напоминания за 24 и за 2 часа до встречи, пользователь выбирает в настройках.
- Групповые чаты: оба варианта — `/new` в группе (бот присылает кнопку, после создания публикует карточку)
  и отправка карточки из приложения в любой чат. В группу бот публикует только карточку и итог.
- Администратор — владелец, Telegram ID `1979217645`. Статистика — экран в Mini App, виден только администратору,
  плюс короткая команда `/stats` в личке с ботом (отвечает только администратору).
- Тон сообщений нейтральный, на «вы», без лишних эмодзи: подходит и для свидания, и для шашлыков.
- Включить `pg_net` (очередь уведомлений), inline-режим бота включён владельцем (подсказка «Найти встречу»).
- Автодеплой Edge Functions через GitHub Actions — после того как владелец добавит секрет `SUPABASE_ACCESS_TOKEN`.
- Владелец разрешил менять архитектуру, если это оправдано.

### Этап 2. Города, места и безопасность открытых встреч

**2.1 Города.**
- Справочник `cities` (Минск + 5 областных центров, поле `timezone`, `is_active`).
- У встречи и пользователя появляется город; лента «Открытые встречи» фильтруется по городу.
- Часовой пояс берётся из города вместо захардкоженного `Europe/Minsk` (сейчас в 4 местах).

**2.2 Категории встреч.** Например: кофе, бар, спорт, настолки, прогулка, кино, концерт, активный отдых.
Фильтр и поиск по названию в ленте.

**2.3 Каталог заведений.**
- Таблица `venues`: город, категория, название, адрес, координаты, ценовой уровень, ссылка, источник, статус модерации.
- Первичное наполнение Минска — импорт из OpenStreetMap (лицензия ODbL, обязательна атрибуция) + ручная
  курация владельцем. Платные API (Google, Яндекс, 2ГИС) — не сейчас.
- В шаге «Где?» мастера создания — подборка заведений по категории и бюджету встречи; выбор добавляет вариант места.
- Экран «Куда сходить» — подборки по городу и категориям, из карточки можно сразу создать встречу.
- Модель данных готова к будущему «продвижению заведений» (монетизация), но сейчас без него.

**2.4 Безопасность встреч с незнакомыми.**
- Роль администратора (по `telegram_user_id`) — владелец.
- «Пожаловаться» на открытую встречу и на участника; жалоба сразу приходит администратору в бот.
- Инструменты администратора: скрыть встречу, заблокировать пользователя (не может создавать открытые
  встречи и подавать заявки), просмотр жалоб.
- Пользователь может заблокировать другого (не видит его встречи и заявки).
- Rate limit: создание встреч, заявки, предложения вариантов, жалобы (лимиты на пользователя в час/сутки, в БД).
- Короткие правила сообщества при первом входе в «Открытые встречи».

**Решения по 2.4 (2026-10-14, лимиты предложены Claude по поручению владельца, можно поменять):**
на пользователя — открытые встречи 2 в час / 5 в сутки; любые встречи 10 / 30; заявки на участие 10 / 30;
предложения вариантов 20 / 50; жалобы 5 / 10, одна жалоба на одну и ту же встречу или человека. Ответы и голоса
не ограничиваются. Правила сообщества пишет Claude, владелец согласует.

Приёмка: лента по городу и категории; подборка мест в мастере; жалоба доходит до администратора за минуту;
заблокированный пользователь не может создавать открытые встречи; лимиты покрыты тестами.

- Telegram может не доставлять сообщения тем, кто не дал разрешение — поэтому 1.1 обязателен.
- Встречи с незнакомыми — репутационный риск; этап 2.4 не выкатывается частично.
- Качество данных OSM по заведениям Минска неполное — нужна ручная курация.
- Владелец — единственный модератор: важны лимиты и быстрые инструменты блокировки.
